# Assumptions

## Technology and runtime

- The service runs on Node.js 20 or newer.
- MongoDB is used for persistent account and transaction data.
- Express handles HTTP routing, and Mongoose defines the database schemas.
- Request validation is performed by Zod.
- Currency values are represented as JavaScript and MongoDB numbers rather than decimal or integer minor-unit types.

## Configuration

- The server uses `PORT` from the environment, with `5000` as the default implementation value in this project.
- `MONGODB_URI` must identify the MongoDB database used by the service.
- The database user must have permission to read and write accounts and transactions and to create or verify indexes.

## Accounts

- Account IDs are supplied by API clients and are not generated by the server.
- Account ID and name are both required.
- Account IDs and names are trimmed before storage.
- Account IDs are globally unique.
- Every newly created account starts with a balance of `0`.
- A client cannot set the initial account balance through the create-account request.
- Negative balances are not allowed by the account schema.

## Transactions

- Each transaction must include an account ID, reference ID, type, and amount.
- `credit` increases the balance and `debit` decreases the balance.
- A debit must not exceed the current balance.
- Amounts must be finite and greater than zero.
- Monetary units are not implicitly converted or rounded by the API.
- No currency, rounding policy, or precision policy is defined in this application.
- The description is optional, trimmed, and limited to 500 characters.
- Transactions are immutable from the API's perspective.
- There are no update or delete endpoints for transactions.

## Idempotency and uniqueness

- A transaction reference ID is unique within an account, not necessarily across different accounts.
- Two accounts may use the same reference ID because uniqueness is enforced by the compound account ID and reference ID index.
- Repeating the same reference ID for the same account returns `409 Conflict`.

## Ordering and history

- Transaction history is returned newest first by creation time, with `_id` as an additional deterministic ordering key.
- `page` is one-based.
- `limit` has a maximum of `100`.
- An empty result page can have zero transactions and zero calculated total pages.
- Type filtering is optional and supports exactly `credit` or `debit`.

## MongoDB consistency

- For a replica-set deployment, transaction creation and balance updates are performed in a MongoDB session transaction.
- For a standalone MongoDB deployment, the API uses a development compatibility fallback because standalone MongoDB does not support the required sessions transaction flow.
- The standalone fallback has only partial atomicity: it may need compensating cleanup if the balance update fails after transaction creation.
- The standalone fallback is intended for local development and testing, not production or concurrent workloads requiring transactional integrity.
- Production deployments should use MongoDB replica sets with transaction support enabled.

## API conventions

- Request and response bodies use camelCase field names.
- Validation failures return HTTP `400` and a field-level `details` array.
- Missing accounts and unknown routes use HTTP `404`.
- Duplicate identifiers use HTTP `409`.
- Unexpected server failures return HTTP `500` with a generic message so internal details are not exposed.

## Out of scope

- Authentication and authorization are not implemented.
- User roles and account ownership are not modeled.
- Transfers between two accounts are not implemented.
- Multi-currency accounts are not supported.
- Reversals and transaction adjustment endpoints are not implemented.
- Audit history for account updates is not implemented.
- A compensating ledger correction workflow is not included.
